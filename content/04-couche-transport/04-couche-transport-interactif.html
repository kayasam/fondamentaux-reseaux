04. Couche transport

TCP vs UDP, numéros de ports, handshake, et outils de diagnostic couche 4.

Rôle de la couche transport

La couche 4 assure le transfert des données entre deux applications sur des machines différentes :

  • Segmente les données en unités transportables
  • Identifie les applications via les numéros de port
  • Choisit entre fiabilité (TCP) ou rapidité (UDP)

Une socket = adresse IP + port. Exemple : 192.168.1.10:443 identifie un serveur HTTPS.

Session réseau
Un serveur écoute sur un port fixe (ex. 443). Le client utilise un port temporaire (ex. 51324) pour la réponse. La session est identifiée par le quadruplet : IP src + port src + IP dst + port dst.

UDP — User Datagram Protocol

UDP envoie des données sans établir de connexion et sans vérification de réception. C'est le protocole "fire and forget".

Structure d'un datagramme UDP

Cliquez sur un champ :

Port Source16 bits
Port Dest.16 bits
Longueur16 bits
Checksum16 bits
Donnéesvariable
Port Source (16 bits) — Port de l'application émettrice. Permet au destinataire de savoir où envoyer la réponse.
Port Destination (16 bits) — Port de l'application réceptrice. Ex. : 53 pour DNS, 67 pour DHCP.
Longueur (16 bits) — Taille totale du datagramme (en-tête + données). L'en-tête UDP fait seulement 8 octets → très léger.
Checksum (16 bits) — Vérification d'intégrité optionnelle. Détecte les erreurs mais ne retransmet pas si le datagramme est corrompu.
Données (variable) — Le contenu utile envoyé par l'application (requête DNS, paquet VoIP, etc.).
Pourquoi UDP est si léger
L'en-tête UDP ne fait que 8 octets (vs 20+ pour TCP). Pas de handshake, pas de numéros de séquence, pas d'acquittements. Résultat : latence minimale et overhead quasi nul.

ApplicationPourquoi UDP ?

TCP — Transmission Control Protocol

TCP garantit que les données arrivent dans l'ordre, sans perte et sans erreur.

Structure d'un segment TCP

Cliquez sur un champ :

Port Src16 bits
Port Dst16 bits
N° Séquence32 bits
N° Acquit.32 bits
FlagsSYN ACK FIN…
Fenêtre16 bits
Donnéesvariable
Port Source (16 bits) — Port de l'application émettrice (souvent un port dynamique côté client).
Port Destination (16 bits) — Port de l'application réceptrice. Ex. : 443 pour HTTPS, 22 pour SSH.
Numéro de séquence (32 bits) — Identifie la position des données dans le flux. Permet au récepteur de réassembler les segments dans l'ordre, même s'ils arrivent dans le désordre.
Numéro d'acquittement (32 bits) — Indique le prochain octet attendu par le récepteur. Confirme la bonne réception de tous les octets précédents. Si un segment n'est pas acquitté → retransmission.
Flags — Bits de contrôle : SYN (ouverture), ACK (acquittement), FIN (fermeture), RST (reset), PSH (push immédiat), URG (urgent). Combinés pour gérer l'état de la connexion.
Fenêtre (Window, 16 bits) — Nombre d'octets que le récepteur est prêt à accepter. C'est le mécanisme de contrôle de flux (fenêtre glissante) : empêche l'émetteur de saturer le récepteur.
Données (variable) — Le contenu utile de l'application (page HTML, e-mail, fichier…).

Fermeture de connexion (4 étapes)

Chaque côté ferme sa moitié de la connexion :

  1. Client → FIN → Serveur
  2. Client ← ACK ← Serveur
  3. Client ← FIN ← Serveur
  4. Client → ACK → Serveur → le client passe en TIME_WAIT
Cliquez étape par étape pour voir la fermeture TCP.

Mécanismes clés de TCP

  • Numéros de séquence — réassemblage des segments dans l'ordre
  • Acquittements (ACK) — chaque segment reçu est confirmé
  • Fenêtre glissante — contrôle de débit pour éviter la saturation du récepteur
  • Retransmission — segment non acquitté → renvoi automatique

Outils de diagnostic couche 4

Un diagnostic couche 4 se joue à trois endroits différents. Cliquez sur un poste pour voir quelle commande lancer, où, et ce qu'elle répond :

CLIENT

Le port distant est-il joignable ?

→

RÉSEAU

Que voit-on passer sur le fil ?

→

SERVEUR

Le service écoute-t-il vraiment ?

Sur le poste CLIENT — tester un port distant

À taper sur la machine qui essaie de contacter le service, pas sur le serveur.

# Linux — test applicatif (le service HTTP répond-il vraiment ?)
curl -I https://203.0.113.10

# Linux — test du port seul, sans dépendre d'un protocole applicatif
nmap -p 443 203.0.113.10
  • -I (curl) : ne récupère que les en-têtes HTTP, pas la page entière → confirme qu'un serveur web répond bien sur ce port.
  • -p 443 (nmap) : limite le scan à ce port précis → répond open, closed ou filtered.
# Windows PowerShell
Test-NetConnection 203.0.113.10 -Port 443
  • -Port 443 : port à tester → la commande tente une connexion TCP et renvoie TcpTestSucceeded : True/False.
Pourquoi pas telnet / nc ?
Ces outils historiques ne sont plus installés par défaut sur la plupart des systèmes récents. nmap, curl et Test-NetConnection couvrent les mêmes besoins et sont les outils réellement utilisés aujourd'hui.
Entre les deux — observer les échanges (Wireshark)

À lancer sur un poste qui peut capturer le trafic (le client, le serveur, ou un équipement intermédiaire en miroir de port).

tcp.port == 443
tcp.flags.syn == 1
udp.port == 53
  • tcp.port == 443 : n'affiche que les paquets liés à ce port, dans les deux sens.
  • tcp.flags.syn == 1 : isole les segments d'ouverture de connexion (handshake).
  • udp.port == 53 : isole les échanges DNS.
Sur le poste SERVEUR — vérifier qu'un service écoute

À taper sur la machine qui est censée héberger le service, avant même de tester depuis le client.

# Linux
ss -lntup
  • -l : uniquement les sockets en écoute (listening).
  • -n : adresses et ports en numérique, sans résolution DNS (plus rapide).
  • -t : connexions TCP.
  • -u : connexions UDP.
  • -p : affiche le processus qui écoute sur chaque port.
# Windows PowerShell
Get-NetTCPConnection -State Listen
Get-NetUDPEndpoint
  • -State Listen : ne garde que les connexions TCP en attente d'une connexion entrante.
  • Get-NetUDPEndpoint : liste les ports UDP ouverts (UDP n'a pas d'état « Listen »).

États TCP courants

ÉtatSignificationDiagnostic

Astuce
Un port en LISTEN mais inaccessible de l'extérieur → problème de pare-feu. Beaucoup de TIME_WAIT → serveur très sollicité ou mal configuré.
